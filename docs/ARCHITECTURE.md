## 状态模型

`Root` 是 GPUI 侧唯一根实体。子模块不保存第二份全局状态，只读 `&Root` 或通过
`cx.listener` / entity update 派发动作。列表滚动句柄、菜单位置、搜索输入等 UI 状态
放在 `Root`；缓存数据用 `Arc` 共享，避免渲染路径深拷贝。

当前曲目的取值顺序是：

```text
pending_track（正在装载的新歌）
  → queue.current()（已生效的当前歌）
```

这样可以避免切歌时出现“界面显示 A、耳朵听到 B”的竞态。

反馈分两条通道，各管一件事：

- **状态行**（`Root::status_line` → `ui::status_line`）：普通操作反馈（切档、开关、
  收藏、加载中…）的固定出口，渲染在播放栏上方，5 秒后消失，切页清空。写入方只管
  「写什么」；去重、超时与切页清空都在这一处。唯一要留意的是顺序——会被切页清空的
  确认，要写在切页之后。
- **全局 message**（`ui::message`）：需要用户注意的事件（登录、快捷键冲突、
  拉流或读取失败）。同一来源用稳定 key 替换，最多同时 4 条。这类事件同时写状态行：
  轻提示 3 秒就走，负责「叫住你」；状态行留到 5 秒，负责「留下来说过什么」。
  轻提示的 3 秒按**产生时刻**算（#212）：Info/Success 晚到只显示剩余、过期的直接
  不显示；Error/Warning 不按时间过期，关窗期间留着。这里要分清两种消失：
  **按时间过期**（只裁 Info/Success）和**按容量驱逐**（超过 4 条时的腾位规则）——
  所以 Error/Warning 只是不因时间过期，队列满时仍可能被挤掉。
  补弹讲一次：只有**还没渲染过**、留到重开的那条才拿到完整时长；关窗前已经画过的
  保持原计时和剩余时长，不会重新计满。腾位时先挤最旧的普通提示；没有普通提示可挤
  时，新来的普通提示直接不显示（3 秒的事，不换掉一条错误），新来的 Error/Warning
  才挤掉最旧的那条。刚入队这条永远不参与这次淘汰。

## 配置与环境变量

启动时 `Settings::merged_with_env` 用 `SODA_COOKIE` 等环境变量补空字段；配置文件被外部
改动会热重载，重载时同样补环境变量（#185）。例外：用户在界面上显式登出后，本次运行里
热重载不再用 `SODA_COOKIE` 补回 Cookie（#192）。这个记号不落盘，重启后仍按环境变量启动；
它只在扫码登录成功、或外部把非空 Cookie 写进配置文件并被热重载应用时解除。

## 线程与异步

libresoda 的 HTTP 和下载是阻塞的；GPUI 渲染不能阻塞。规则如下：

1. 网络请求、文件下载、解密、封面缩放放到 `cx.background_spawn` 或专用线程。
2. 完成后用 `cx.spawn` + entity update 回到 GPUI 实体上下文，然后 `cx.notify()`。
3. 带分页 / 可取消语义的请求使用 `request_seq` 丢弃过期结果。
4. 封面状态收在 `sodam-core` 的 `CoverStore`：缩略图和原图各一格，有界并发、
   一条 URL 一条记录；渲染路径只查内存快照。
5. 音频线程独立于 GPUI，通过 channel 接收命令，通过 snapshot 共享状态。

## 播放链路

```text
TrackItem + cache path
  → CachedTrack（本地路径、音质、缓存租约）
  → PlaybackEngine::load(track, cached) → 装载序号
  → rodio Decoder + Sink
  → snapshot: track_id / title / playing / position / duration / quality / error
```

播放结束时音频线程标记 `finished` 并递增 `finished_seq`；GPUI 心跳据此自动续播：普通模式
先按不可播集合选下一个可播候选（`Queue::advance_playable`），单曲循环仍走「播完重播」语义
（自动路径，不算用户主动播放）。播放或装载中、有未处理的完成事件、有新 `error_seq` 时，
心跳走 200ms 热档；暂停且没有这些事件时走 1s 空闲档。空闲档仍取一份 snapshot 喂播放上报，
并跑设置保存尾巴（写错误与音量拖动收尾）、推荐补货（条件解除时撤下整圈无候选提示）、
每 5s 预取巡检、按到期规则跑缓存维护，不推进进度条重绘。用户播放、暂停或开始装载时会叫醒等待，
按新状态重选档位，不必等满 1s。音量拖动未收尾时也暂留热档，保证停手 600ms 后的落盘兜底
不因空闲档拖到约 1.6s。签名不足或设备不匹配时，libresoda 可能只返回试听；错误会进入状态行或
播放页重试区。

音频装载成功/失败都回执 `load_seq`，心跳据此退出 loading，不再只比较 track id。
输出设备错误或非暂停状态下 15 秒无进度会释放失效输出并报告错误；用户再次点播放时
重新装载缓存、打开设备，不会因为启动/休眠后的一次设备失败而永远不可播放。

系统默认输出设备被切换时（音响 → USB 耳机），播放线程每 2 秒探测一次默认设备 ID，
变化后换新输出并从原位置续播 —— Windows(WASAPI) / macOS(CoreAudio) 的流在创建时就
绑死设备，不重建就得重启应用才生效。Linux 的 cpal ALSA 后端恒为单一的 `default` 设备，
现有流由 PipeWire/WirePlumber 自动迁到新的默认节点，因此探测不会触发（行为与修复前一致）。

歌词 ticker 在没有窗口时睡 1s；判断 `cx.windows()` 仍需借一次 app 上下文，所以地板是每秒一次，
这次借用也计入 loop probe 的 app 次数。有窗口但不在歌词页时仍走 120ms 空闲档；只有确实要
`notify` 时才进第二次实体更新。

## 设置落盘与磁盘缓存

- `SettingsWriter` 是唯一的设置写者：界面上改完设置只把整份快照排进这条后台队列，
  300ms 内没有新改动才落盘，所以连着拖音量、连点几个开关都只写一次盘。启动期欠下的
  回存（隔离坏文件 / 迁移回存 / 刷备份）和登出摘 Cookie 也排在同一条队列里，
  退出时只等一次 `flush()`（#259）。
- 扫码登录成功那一次例外：界面线程当场写盘，否则「登录成功后三秒内退出」会丢 Cookie。
- 排队落盘的快照 Cookie 一律沿用盘上那份（`Settings::save_queued_to`）：登录、登出之外
  的保存带不回旧身份，慢一拍落盘也不会把刚登进去的新 Cookie 换掉。
- 普通设置写失败在下一拍（心跳热档 200ms / 空闲档 1s）进状态行；启动期回存失败由托盘的
  100ms 拍报告，退出等待期间不消费这条提示。所有配置写入用同一进程内锁和同目录原子替换。
- `cache` 默认限制音频为 10 GiB，设置页可调整；维护在后台线程跑，不在渲染线程扫盘。
  常规轮次里，一轮维护对音频树、封面树各只扫一遍，配额淘汰、暂存清扫、统计都吃同一份盘点结果；
  未超上限的树连分组排序都不做。进设置页另有一次一次性统计扫描（`audio::cache_stats`），
  与维护这条路径无关。心跳每 60 秒只问一次「到期没」：上次维护的完成时刻与当时的占用
  落盘在缓存根的 `maintenance.tsv`（进程重启不清零），常规 6 小时一轮；已用摸到九成时
  30 分钟查一次；上一轮有子树读不全时也按 30 分钟重查（那次的字节只是下界）；已知超限时
  10 分钟重试（播放中的文件会被租约挡住，重试不能按分钟来）。改上限若正撞上批量升级/清缓存，
  请求会记下来等收尾后补跑。
  两次看盘之间的写入另有一本进程内的增量账（`cache::AUDIO_DELTA`，一个原子计数，不加锁）：
  每次下载尝试在动手之前先量一遍暂存族多大（含马上会被清掉的残留交付目标），失败/中止时
  只记这次长出来（或缩掉）的差额；落进正式缓存时改记「加新减旧」（新音频与边车减掉被换掉
  的旧文件），暂存那截只按这次长了多少算。续传、重试因此只补自己这次的增量，跨过一次看盘
  也不会把扫描已经算过的那段再加一遍。账本只用来把检查提前：心跳每拍读一次净增量，上次
  看盘还没到九成、这本账把音频占用推过九成时立刻跑一轮，不等 60 秒那一拍；扫描一开始账本
  就整本作废，新数字以这一轮扫描为准，所以手动删目录、换缓存位置下一轮自然纠正。停在九成
  以上时不再按账本反复触发，仍由上面的密集档兜住——否则删不动时写一首就会扫一遍盘。
  维护日志 `cache_maintenance` 记 `duration_ms` / `scanned_files` / `removed_files` /
  `audio_bytes` / `skipped_reason`（`none` / `below_limit` / `blocked` / `over_limit` /
  `*_incomplete`）、`audio_gap` / `cover_gap`（`none` / `dir` / `entries` / `metadata`，
  读不全时写明缺口落在哪一层）、`audio_incomplete`（0/1，为 1 时 `audio_bytes` 只是下界）
  与 `over_limit` 字段（#310；`audio_bytes` 是这一轮扫完、删完之后的音频树总量，
  日志里就能和磁盘上的实际占用对账）。
  两棵树的用量统一用 `cache::CacheUsage` 表示：字节、文件数、歌曲数，加一个「这轮读全了没有」；
  维护报告与进设置页的一次性统计（`audio::cache_stats`）都产出它。读不全时这几个数只是下界，
  设置页写成「至少 X」并跟一句「有缓存文件暂时读不到，数字可能偏小；稍后会自动重试」，
  不写具体原因（代码只知道没读到，分不清是被别的程序占着还是没权限）；整棵树一个文件都没
  读到时那一段写「读不到」而不是 0 B（`CacheUsage::unreadable`），两棵树都这样就不再写总数。
  手动清空返回 `cache::ClearReport`，提示里说清这一轮有没有读全。
  规模基准一条命令：`cargo run --release -p sodam-core --example cache_bench`，造
  1000 / 5000 / 20000 个文件各跑一轮，输出耗时、扫描文件数、删除数；入口是
  `cache::maintain_in`，不碰全局缓存根。
  实际缓存命中更新音频 mtime，巡检的 `is_cached` 不刷新最近使用时间。
- `CacheLease` 从下载/缓存命中，经后台返回值、音频命令一直传到播放器寿命结束，
  淘汰与手动清理都跳过被租用的音频及其 sidecar。同一缓存目标的下载写者串行化。
- `.quality` sidecar 按制表符分十段：档位、字节数、是否试听、实际档位分数、已探测目标档位、
  探测时间、补整曲尝试时间、未知档探测目标、未知档探测时间、账号/VIP 范围指纹。后七段是逐步
  加上去的，缺段的旧记录按「未知」读，不影响命中判定；第 4 段也可能是空串——档位未知的旧缓存
  记下「已探测过目标档位」之后就是这个样子。第 5、6 段记录「用当时账号向服务端要过哪个档位、
  没拿到更高流」，30 天后过期重探；记录按当时账号算，换号或会员权益变化不会立刻作废，最多等到
  过期再试。第 7 段只给试听片段用，记上次为补整曲重新取流的时间，退避期内不再自动重下。
  第 8–10 段只记录「完整流探测过但档位未知」：不写实际档位，也不写确认性 miss；同账号/VIP 范围、
  同目标退避 30 天，换号、权益变化、目标变化、过期、时钟回拨或范围缺失会解除这层限制，是否真的
  重试仍要过其余升级判定。试听、未知档探测与确认结论不能互相冒充。档位未知时界面就说未知，
  只有旧「无损」标签允许按无损下限抑制一次注定没有收益的重下。
- 清理不跟随符号链接，覆盖封面原图子目录；上限是软上限：受保护文件允许暂时超额，
  释放后由下一轮维护淘汰。音频下载暂存（`staging/` 子目录，libresoda 可续传的
  `.part` / `.part.meta` / `.dec.tmp` 等，名单见 `cache::STAGED_SUFFIXES`）有两道收尾：
  每轮维护按 7 天保留期**整族**清扫过期残留：族里任一成员还年轻就整族保留，不在边界上
  拆开续传对；`.part.lock` 永不删——它的 mtime 停在首次下载，删掉正被内核锁挂着的锁会
  让后到的下载者另立新锁、破坏跨进程互斥。staging 这一层没整个看见时整轮跳过——
  看不到的可能是族里最新的一员，见过的那几条会显得「整族都过期」；缺口不在这层、
  也不在它的上层路径上（这层确实列全了）时，照常清。启动后的首轮维护另清一次音频根**顶层**的旧格式
  （#241 之前）非锁残留——只列这一层、不递归，`staging/` 里的交给上面那条 7 天清扫；认族只
  看文件名后缀（`is_staged_part`），所以这一层里哪怕是不相干的 `notes.txt.part` 也算
  残留、到龄一起清。24 小时门槛 + 租约 + 进程级一次性门（`legacy_residue_swept` 记删除数；
  目录没读全这轮不算数、下轮重试，连续 5 轮不完整就放弃，
  `legacy_residue_sweep_incomplete` / `legacy_residue_sweep_gave_up` 两条 Warn 留痕）。
  配额超额时续传族同样按整族保护，不会被淘汰拆开。
- 音频与封面共用同一份递归扫描（`cache::scan_files`）和同一个按组 LRU 淘汰器，两者只在
  分组键（`{track}-{tag}` vs. 封面 URL 哈希）和删除方式（租约检查 vs. 直接删）上不同。
  扫描区分「目录不存在」和「子树读不到」：前者按空目录正常处理，后者把扫描标成不完整，
  可读部分照旧收进来，并记下缺口落在哪一层（`ScanGap`：`dir` / `entries` / `metadata`）
  与每一处缺口的路径，维护报告与日志用它说明这一轮为什么没读全，也用来判断某一层
  （如 `staging/`）是不是整个看见了。不完整扫描下，封面只在「可读部分自己已超限」时按它淘汰（真实占用
  必然也超限，删掉的确实是可读文件里最旧的），否则本轮不删；两种情况都写一条 Warn 日志
  `cover_trim_incomplete`（`readable_bytes` / `readable_files` / `action`），同一个动作只写
  一次，扫描恢复完整后复位。读不到的那部分有多大无从得知，目录可能停在限额之上，这条日志
  是唯一的线索。音频维持既有口径，只看可读部分淘汰：额度是用户设的，少删比不删更接近预期。
- 封面淘汰的排序键是 `max(mtime, 最近显示时间)`：渲染时 `load_at` 在每次布局/绘制命中时
  同时更新内存缓存 LRU 的 `Instant` 和磁盘淘汰用的墙钟显示时间；后台维护前在渲染线程采样
  一次（`CoverImageCache::last_shown_times`）传给淘汰器。墙钟时间与 `Instant` 分开记录，
  系统挂起恢复后不会把旧记录“推新”。快照只覆盖仍在内存缓存里的封面，其余退回 mtime；
  启动时若到期，首轮维护在首帧之前跑，那时快照还是空的，因此仍按 mtime 淘汰。mtime 在磁盘缓存命中时也会更新，
  所以两者取较晚者，避免常看的封面因旧 mtime 先被删。
- 封面（缩略图与原图）落盘走 `cache::write_cache_file_atomic`：先写同目录的 `.part` 临时
  文件，整份写好再一次性换到正式文件（`rename` 在三个平台上都是覆盖式的）。换不动时只删
  自己的临时文件，旧封面一动不动；所以正式路径上要么是旧封面，要么是整份新封面。
- 预取巡检约每 5 秒补一次。全局故障（登录过期 / 签名服务不可用 / 磁盘写满 / 缺 Cookie）
  期间整条管线挂起，恢复信号按故障类分：重新登录成功、用户主动播放、或 60 秒兜底冷却。
  冷却从挂起时刻算，`expire_cooldown` 只在**未落闸**的预取巡检拍上调用；落闸期间这条巡检
  不排新预取，实际恢复顺延到用户主动播放后的下一拍。装载成功、切档、下一首播放等显式触发点
  仍各自调用 `spawn_prefetch`，但同样受管线闸门约束。挂起只在日志留痕，不打扰用户
  （见 `sodam_core::prefetch`）。
- 预取的逐曲失败只做 60 秒冷却；按曲目结论进不可播集合，全局故障挂管线闸门，
  两者都不进冷却表，因此不会出现「永不过期」的逐曲黑名单。账号 / 会员状态变化时，
  冷却表与不可播集合一并作废。

## 导航与详情页

`Nav` 包含固定入口和详情页：`Discover`、`Listening Modes`、`Search`、`Liked Music`、
`My Playlists`、`Artist`、`Album`、`Settings`、`Now Playing`。

## 队列与历史

`Queue` 保存曲目列表和当前索引；播放后的曲目进入 `played_history`。
队列展示分为已播放、正在播放、接下来三段。

播放模式有三种，对齐官方客户端的 `QueuePlayOrder`，点击按
「列表循环 → 单曲循环 → 随机播放」轮换，存在 `Settings.play_mode`：

- **列表循环**：播到末尾回到第一首。
- **单曲循环**：停止在同一首，由播放器决定是否重播。
- **随机播放**：不洗牌队列本身（抽屉里仍是真实曲目顺序），而是预生成一整轮
  待播下标 `shuffle_round`，`advance` 依次取用；一轮播完立即重建并清空
  `history`。`history` 记录走过的下标，「上一首」沿它回退到真正播过的那首，
  `redo` 让「上一首 → 下一首」原路返回。

`shuffle_round` 与 `history` 存的都是下标，所以队列变更必须同步：
`remove` 左移、`insert_next` 右移并把新项插到轮次首位、`jump` 把目标从轮次
剔除（否则会重播）。「接下来」由 `Queue::upcoming()` 给出，与真实播放顺序一致。

不可播集合（`failure::UnplayableTracks`）记录当前账号在本会话内确认放不出来的曲目：
只由按曲目类失败写入，全局故障不写，账号 id / 会员状态变化整份作废，仅存内存。
`next_playable` / `advance_playable` 据此跳过命中项并同步随机轮次；整圈无候选时
落闸并把「这一轮没有能播的歌了」留在常驻错误位，条件解除后自动撤下。
用户显式点播命中集合的曲目（列表行、队列项、播放键）时不换歌、不发装载请求，
直接用集合记住的成因给出按曲目类文案；拦截发生在改队列之前，播放状态与当前曲目
都不动，单曲循环下同样不会触发自动前进。条目仍可点击；已落盘的**整曲**缓存先于
结论（试听片段不算）。
启动时「自动装载第一首但不播放」的那条路（`pause_pending`）用同一个判据换歌
（`PlaybackFailure::is_per_track`）：关于某一首的失败先记进集合再让队列推进，
换到了继续只装载、不替用户按下播放，换不到就说整圈没有能播的歌并落闸；
全局故障与网络抖动都不换歌，照旧提示，并同样挂起预取管线——这条路还没播过声音，
所以全局故障只给提示，不落闸。

点播与自动续播的失败后果由 `play_failure::decide_play_failure` 纯决策产出：记账、提示
槽位与渠道、前进方式、落闸方式。调用方只执行结果，身份校验与预取挂起仍留在决策之前。
预装路径暂不接入：它只试一次、不累计连败，也没有点播的原地重试与连败封顶；13 行验收由
12 行纯决策表和 1 行身份门测试组成，预装代码仍保持原样，等第二刀再决定是否对齐。

推荐 / 听歌模式 / 电台这类无限流不显示模式按钮，并强制列表循环——那边的歌
由服务端持续追加，单曲循环会让流停住。

## 打包与运行时

- Linux ARM64 使用 `packaging/arch/PKGBUILD` 生成 pacman 包；
  x86_64 / aarch64 另用 `packaging/deb/make-deb.sh` 从同一份 release 二进制打 `.deb`。
- Linux x86_64 的发布包按 x86-64 baseline 构建：x86_64 的 runner 钉在 `ubuntu-24.04`
  （26.04 的镜像默认用 amd64v3 变体的 GCC，C 依赖会带上 AVX2/BMI2，没有这些指令的老 CPU
  一发起 HTTPS 就 SIGILL，见 #306）。构建时另给 C 代码钉 `-march=x86-64`，构建完再用
  `scripts/check-x86-64-baseline.sh` 扫一遍产物兜底。
- 安装内容：`/usr/bin/sodam`、desktop entry、hicolor icon。
- GUI 通过 `scripts/run.sh` 启动时带 `MemoryMax=2G` 护栏。
- 托盘和窗口关闭逻辑使用显式退出模式：关闭主窗口保留进程，退出走托盘菜单。
- 应用内退出（托盘 / ⌘Q）先过 `sodam-core` 的退出闸门：状态行提示「正在保存…」，
  等设置写队列 `flush()` 刷干净（排队中的改动、启动回存、登出摘 Cookie 都在里头）
  再 `cx.quit()`；最长等 3 秒，到点强制退出并写日志。再次点击退出立即退出；
  这两条强制路径不再等写线程 `join`，避免慢盘把进程挂住。GPUI 的 `on_app_quit`
  只留 200ms 兜底，只覆盖 GPUI 能执行退出回调的路径；SIGKILL / 任务管理器强杀
  不执行任何回调，这类路径只能等下次启动重做。
