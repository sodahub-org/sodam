开发者文档

SodaM 是一个 Rust workspace：sodam-core 是纯领域层，sodam 是 GPUI 应用。 音乐能力来自 libresoda， 应用签名来自 libmssdk。

环境要求

项目要求
Rust1.85+（workspace rust-version）
Linux 依赖alsa-lib dbus fontconfig freetype2 hicolor-icon-theme libxkbcommon libxcb
macOSApple Silicon，Xcode Command Line Tools
Windowsx64，MSVC 工具链

构建与运行

仓库自带带内存护栏的脚本（这台开发机 15GB 内存，GPUI 编译较重，曾出现过 OOM）：

常用命令
git clone https://github.com/sodahub-org/sodam
cd sodam

scripts/check.sh   # cargo check + fmt --check + clippy -D warnings + test
scripts/build.sh   # 构建（默认 debug，--release 出正式包）
scripts/run.sh     # 启动 GUI（带 MemoryMax 护栏，编译时不要跑）
资源护栏：编译时不跑 GUI、跑 GUI 时不编译；卡顿时先看 journalctl -k | grep -iE "drm|flip_done|oom"。

提交前必须跑 scripts/check.sh；UI 改动必须用 scripts/run.sh 真机验证，不能只过 cargo check。

目录结构

路径职责
crates/sodam-core/领域层：配置、会话、队列、音乐库、播放引擎（不依赖 GPUI）
crates/sodam/GPUI 应用：入口、Root 状态、动作、托盘、ui/、views/
packaging/arch/PKGBUILD、desktop 文件、mkrepo.sh（生成 pacman 源）
packaging/homebrew/Homebrew Cask
website/本官网（静态页面，CI 部署到 GitHub Pages）
docs/ARCHITECTURE / ROADMAP / UI-SPEC
scripts/check / build / run（带内存护栏）

架构要点

  • 领域层不依赖 GPUI：sodam-core 是纯 Rust，可单独测试。
  • 渲染线程不阻塞：libresoda 的 HTTP / 下载是阻塞操作，必须放在 cx.background_spawn 或专用线程，结果回 UI 后 cx.notify()。
  • 状态只有一处：播放、队列、导航、设置由 Root 或 core 模型持有；UI 只读状态、生成元素、派发动作。
  • 音频线程独立：rodio 的 OutputStream 是 !Send，所以音频对象全留在 sodam-audio 线程，UI 通过命令通道操作、通过 PlaybackSnapshot 读状态。
  • 错误不 panic：网络/配置错误写进 Root::status 或页面提示；只有启动期不可恢复错误才允许 panic。
  • 播放跟随系统默认设备：音频线程每 2 秒探测默认输出设备 ID，变化时重建输出并从原位置续播。

更详细的线程模型见仓库 docs/ARCHITECTURE.md。

开发约定

  1. 接口能力先在 libresoda 打通：SodaM 只做调用与展示，不绕过 libresoda 直接请求汽水接口。
  2. 凭据不入库、不入日志：Cookie、签名 Token、抓包签名头、真实设备指纹禁止提交或打印。
  3. 界面文案走 i18n：新增用户可见文案用 root.tr / root.localized，中文原文作为稳定 key，同步英文词典。
  4. 不引入个人数据：不提交真实 Cookie、签名头、本机路径或账号数据。
  5. UI 改动必须真机验证，提交前跑 scripts/check.sh。

提交与评审

  1. 从 main 切分支：feat/… / fix/… / docs/…。
  2. commit message 用中文祈使句 + 类型前缀：fix(audio): …、feat(ui): …。
  3. 本地跑 scripts/check.sh，UI 改动用 scripts/run.sh 真机确认。
  4. 开 PR，说明「问题 / 原因 / 修复 / 验证」四段；CI 会跑四平台（Linux x86_64 & aarch64、macOS arm64、Windows x64）。
  5. Review 通过后 squash 合并。

发布流程

  1. 改版本号：Cargo.toml 的 [workspace.package] version（Cargo.lock 同步）、packaging/arch/PKGBUILD、README 里的版本示例。
  2. 先由发版工作流生成产物，按 SHA256SUMS 更新 Homebrew Cask 并提交；
  3. 在包含正式 Cask 校验和的提交上打附注 tag，tag message 就是发布说明：
发版
git tag -a v0.3.5 -F changelog.txt
git push origin main
git push origin v0.3.5

CI 会构建四平台产物、创建 GitHub Release，然后自动重建 pacman 源并部署本官网。

  • 用 packaging/homebrew/sync-tap.sh 把同一 Cask 同步到 homebrew-tap 仓库。
  • pacman 源需要补跑时：gh workflow run pages.yml -f tag=v0.3.5。
